# Connecting Grok

**Status: not yet tested with a real Grok client.** Bifrost's MCP interface has been verified locally over stdio and over authenticated loopback HTTP, including raw JSON-RPC calls made the way a hosted MCP client calls a remote server ([verification record](verification.md)). No Grok Bot, Grok web connector or xAI API request has reached Bifrost yet.

What matters for Grok is **where Grok's MCP client runs**. Each route below needs a deliberate decision by the owner of the machine. Bifrost's setup never registers itself with Grok, opens ports, starts tunnels, changes Tailscale or creates credentials.

## Route A: Grok Bot Command server on your own computer

No network listener, token or tunnel.

Grok Bot documents that Command servers run on whichever computer the conversation uses, and that a Bot runs commands on your local computer only when local execution is enabled and approved ([team bots](https://docs.x.ai/grok-bot/team-bots), [approvals](https://docs.x.ai/grok-bot/approvals-security-and-privacy)). When the conversation uses your own computer, Bifrost runs there as an ordinary stdio MCP server.

1. Install Bifrost on Linux, or in WSL2 on Windows, as an ordinary user and on the Linux filesystem ([quick start](../README.md#quick-start)).
2. Put the configuration in a launcher script outside the workspace, owned by you and not writable by others, so the Command and its arguments carry no secrets and no environment variables:

   ```sh
   #!/bin/sh
   export BIFROST_WORKSPACE="$HOME/bifrost-workspace"
   export BIFROST_POLICY="$HOME/.config/bifrost/policy.json"
   export BIFROST_BROWSER_ORIGINS='[]'
   exec /usr/bin/node "$HOME/bifrost-device-mcp/src/cli.js"
   ```

3. In Grok Bot, enable **Settings → General → Bot → Execution on Local Computer**. **Ask every time** keeps Grok's own prompt in front of each command.
4. Add a custom MCP server of type **Command** that runs the launcher. From Windows, run it through WSL, for example command `wsl.exe` with arguments `--distribution Ubuntu-24.04 --user YOUR_LINUX_USER --exec /home/YOUR_LINUX_USER/bifrost-launch.sh`.
5. Check that the Bot can call `session_status`, `terminal_tasks` and a harmless recipe, that unconfigured tasks and paths outside the workspace are refused, and that `permissions_reduce` switches to Ask.

**Limitation:** a stdio process started by Grok has no terminal of yours attached, so Bifrost's owner console (and therefore Ask approvals) is unavailable on this route. Use Auto with a small, harmless recipe list. Anything you would want to approve case by case does not belong in that list.

## Route B: remote HTTPS (Grok Bot remote server, Grok web connectors, xAI API)

Hosted Grok calls the MCP server from xAI's infrastructure, so the URL must be publicly reachable HTTPS. Grok rejects `localhost` and private-network URLs ([tunneling](https://docs.x.ai/grok/connectors/custom-mcp-tunneling)), and the xAI API supports Streamable HTTP and SSE with an `authorization` value placed in the request's Authorization header ([remote MCP](https://docs.x.ai/developers/tools/remote-mcp)).

What this route needs, none of which is done or tested here:

1. **Public ingress**, such as Tailscale Funnel, Cloudflare Tunnel or ngrok, in front of `127.0.0.1:PORT`. This makes the endpoint reachable from the internet; the bearer token becomes the only gate.
2. **A long random bearer token** generated by you, stored outside the workspace, passed to Bifrost as `BIFROST_HTTP_TOKEN` and configured in the client so requests carry exactly `Authorization: Bearer TOKEN`. Check whether your client adds the `Bearer ` prefix itself.
3. **Host handling.** Bifrost accepts only `Host: 127.0.0.1:PORT`. Tailscale Serve and Funnel forward the public `*.ts.net` Host header, so requests through them are refused with 403 today. Either put a reviewed reverse proxy in front that validates the public hostname and rewrites Host, or add an exact external-host allowlist to Bifrost. Neither exists yet. Do not remove the Host check to make routing work.
4. **Local approvals.** Start Bifrost from your own terminal with `BIFROST_TRANSPORT=http BIFROST_MODE=ask BIFROST_APPROVAL_CONSOLE=1`, so each action waits for `approve REQUEST_ID` and `yes` in that terminal. Grok's own approval prompts are not visible to Bifrost and do not count as owner approval.
5. **Acceptance checks** through the real route: a missing or wrong token is refused before any tool runs, a hostile Host or Origin is refused, a harmless call succeeds, a queued action does nothing until you approve it, and stopping Bifrost or rotating the token cuts access.

Keep the token out of URLs, commits, screenshots and chat. See [client compatibility](compatibility.md) and [Tailscale](tailscale.md) for the wider deployment notes.
